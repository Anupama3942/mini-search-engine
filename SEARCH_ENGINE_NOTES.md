# Search Engine Notes

This document contains my personal learning notes from building the Mini Search Engine project. It covers the fundamental concepts of Information Retrieval (IR), Machine Learning (ML) ranking, semantic search, and production deployment.

## 1. Inverted Indexes
An **inverted index** is the core data structure of almost all search engines. Instead of mapping documents to words (like reading a book), it maps words to the documents that contain them (like an index at the back of a book). 
*   **How it works:** It consists of a dictionary of terms, where each term points to a "posting list" — a list of document IDs (and often positions/frequencies) where the term appears.
*   **Why they're fast:** When a user searches for "python programming", the engine simply looks up "python" and "programming" in the dictionary, retrieves their posting lists, and intersects them to find documents containing both words. This is $O(1)$ lookup time per term and efficient intersection, rather than scanning every document (which would be $O(N)$).

## 2. TF-IDF
**TF-IDF** (Term Frequency-Inverse Document Frequency) is a numerical statistic used to reflect how important a word is to a document in a corpus.
*   **Term Frequency (TF):** Measures how frequently a term occurs in a document. High TF means the term is important in that specific document. ($TF = count(t, d)$)
*   **Inverse Document Frequency (IDF):** Measures how rare the term is across all documents. Words like "the" appear everywhere (low IDF), while "kubernetes" is rare (high IDF). ($IDF = \log(N / df)$ where $N$ is total documents and $df$ is documents containing the term).
*   **Formula:** $TF\text{-}IDF = TF \times IDF$.
*   **Why it works:** It rewards words that appear often in a document, but penalizes words that are common everywhere, extracting the true "keywords".

## 3. BM25 (Best Matching 25)
**BM25** is a probabilistic retrieval function and the industry standard for sparse ranking (used in Elasticsearch, Lucene). It improves upon TF-IDF by addressing its flaws.
*   **Formula:** $Score(D, Q) = \sum_{i=1}^{n} IDF(q_i) \cdot \frac{f(q_i, D) \cdot (k_1 + 1)}{f(q_i, D) + k_1 \cdot (1 - b + b \cdot \frac{|D|}{avgdl})}$
*   **$k_1$ Saturation:** In TF-IDF, if a word appears 100 times, it's scored 10x higher than if it appears 10 times. BM25 introduces term frequency saturation ($k_1$, usually 1.2-2.0). After a few occurrences, the score increases very little, acknowledging that seeing a keyword 5 times vs 6 times doesn't mean much difference in relevance.
*   **$b$ Length Normalization:** Long documents naturally have higher term counts. The $b$ parameter (usually 0.75) penalizes long documents so they don't unfairly dominate shorter, highly relevant documents.

## 4. Learning-to-Rank (LTR)
**Learning-to-Rank** applies Machine Learning to optimize search results. Instead of a single static formula like BM25, it uses an ML model to weigh various signals.
*   **Feature Extraction:** For every query-document pair, we extract features like BM25 score, TF-IDF score, document length, term match ratio, page rank, etc.
*   **Pointwise Logistic Regression:** A simple LTR approach where the model looks at one query-document pair at a time and predicts the probability (0 to 1) of it being relevant. The documents are then sorted by this probability.
*   **Why ML helps:** It can dynamically weigh dozens or hundreds of features based on training data, learning complex patterns that a static algorithm cannot capture.

## 5. Embeddings and Vector Search
*   **Embeddings:** These are dense numerical vectors (arrays of floats) that represent the semantic meaning of text. Generated by neural networks (like BERT or OpenAI's text-embedding models). Words with similar meanings are mapped to vectors that are close to each other in high-dimensional space.
*   **Cosine Similarity:** The mathematical metric used to measure the angle between two vectors. A cosine similarity of 1 means identical direction (meaning), 0 means orthogonal, and -1 means opposite.
*   **Why semantic search matters:** Traditional search (BM25) requires exact keyword matches ("lexical search"). Semantic search understands concepts, so searching for "automobile" can find documents about "cars" even if the exact word isn't present.

## 6. Hybrid Retrieval
**Hybrid Retrieval** combines the best of both worlds: the exact keyword precision of sparse search (BM25) and the conceptual understanding of dense search (Embeddings).
*   **Alpha Fusion:** A linear combination formula: $Score = \alpha \cdot DenseScore + (1 - \alpha) \cdot SparseScore$. (e.g., $\alpha=0.5$ gives equal weight).
*   **When to use:** Use hybrid when you need both exact phrase matching (names, IDs, acronyms) and broad conceptual matching. It generally yields the highest overall search quality.

## 7. Two-Stage Retrieval
Running complex ML models or semantic searches over millions of documents is too slow for real-time search. 
*   **Candidate Generation (Stage 1):** A fast, cheap algorithm (like BM25) quickly retrieves the top 1,000 candidate documents from the entire corpus.
*   **Reranking (Stage 2):** A more expensive, accurate algorithm (like LTR or a Cross-Encoder) re-scores only those top 1,000 documents to produce the final top 10 results.
*   **Why it's fast:** It heavily reduces the computational surface area for the expensive ML models.

## 8. Query Understanding
Before searching, we process the user's query to improve results.
*   **Spell Correction:** Fixing typos (e.g., "pithon" $\rightarrow$ "python") using edit distance (Levenshtein) and unigram frequencies.
*   **Synonym Expansion:** Expanding the query with known synonyms (e.g., "fast" $\rightarrow$ "fast OR quick OR rapid").
*   **Intent Classification:** Predicting what the user wants (e.g., informational, navigational, transactional) to route the query to different indexes or apply specific boosting.

## 9. IR Evaluation Metrics
How do we know if our search engine is good? We use a test set with ground-truth relevance labels.
*   **Precision:** Out of all returned documents, how many are relevant? ($TP / (TP + FP)$)
*   **Recall:** Out of all relevant documents in existence, how many did we find? ($TP / (TP + FN)$)
*   **MRR (Mean Reciprocal Rank):** Evaluates where the *first* relevant result appears. If it's at rank 1, score=1. Rank 2, score=0.5. Rank 3, score=0.33. Great for "I feel lucky" or Q&A searches.
*   **MAP (Mean Average Precision):** Averages precision across all recall levels. It rewards engines that return *all* relevant documents near the top. Excellent holistic metric.
*   **NDCG (Normalized Discounted Cumulative Gain):** Accounts for graded relevance (e.g., "Highly Relevant" vs "Somewhat Relevant"). It discounts the value of relevant documents the further down the list they appear.

## 10. Production Architecture
A search engine is only useful if it's reliable.
*   **REST API:** Using Flask/FastAPI to expose search endpoints.
*   **Docker:** Containerizing the application for consistent deployment across environments.
*   **Metrics (Prometheus):** Tracking latency, query counts, and error rates to monitor health.
*   **Rate Limiting & Health Probes:** Preventing abuse via API limits and allowing load balancers (like Kubernetes) to know if the service is alive via `/health` endpoints.

## 11. A/B Testing
To prove a new algorithm is better, we run A/B tests on live users.
*   **Deterministic Hashing:** We hash the user's ID (e.g., `SHA-256(user_id) % 100`) to consistently assign them to Group A (Control) or Group B (Treatment).
*   **Statistical Significance:** Using tests (like Welch's t-test) to ensure the difference in metrics (like click-through rate) isn't just random luck.
*   **Confidence Intervals:** A range of values that likely contains the true effect size (e.g., "We are 95% confident the new algorithm increases clicks by 2% to 5%").
